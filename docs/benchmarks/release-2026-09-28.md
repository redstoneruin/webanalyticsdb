# V1 measured capacity and release evidence

Measurements were taken September 28, 2026, Pacific time. The database uses
durable acknowledgements in every reported workload. Results apply to the named
hardware, schemas, submission patterns and durations; they are not a universal
rows-per-second rating or a long-duration production endurance certification.

The measured 48-byte/64-row-batch cases sustained 30,799 rows/s through the C API
for one minute, 15,030 rows/s with the real console and queries for one minute,
and all 10,000 scheduled rows/s over HTTP for two minutes. Paced C API trials
also completed every scheduled row, but recorded 0.67–5.37-second arrival-to-ack
p99s. These results support workload-specific sizing, not a low-latency SLO.

## Environment and method

The native host is a MacBookPro18,2: Apple M1 Max, 10 CPU cores, 64 GiB RAM,
Darwin 27.0.0, and an internal 8 TB SSD with about 3.2 TB free. Data lives on
APFS with FileVault enabled. Builds used Apple Clang 21, C17, `-O2 -g`, pthreads,
GNU libmicrohttpd 1.0.10 and yyjson 0.12.0. Segment commits use `F_FULLFSYNC`;
directory publication uses `fsync`. No durability setting was relaxed.

The standalone C executable calls the production library; a separate Python
process generates HTTP traffic against a real server. The same workstation
runs the client and server. Deliberate competing builds/tests were stopped for
these measurements; normal workstation background activity was not controlled.
C API CPU/RSS includes its generator. HTTP reports client and server separately.

The [repeated matrix](macos-repeated.json) contains **60 successful workloads**:
20 cases, each repeated three times against a fresh directory. Most have a
10-second arrival window, followed by draining admitted requests. A 512 MiB
logical payload cap bounds disk use. Maximum-size batches reached that cap in
6.9–7.3 seconds; the fixed retention fixture finished in 4.1–4.6 seconds. These
shorter cases are not ten-second sustained measurements.

Every case stops/reopens and compares counts and input-ID sums with successful
receipts. Latencies include generator waiting, input preparation, database queueing
and synchronization. Percentiles are bounded-histogram upper bounds, approximately
3.2% resolution above 32 µs; the tables show medians of the three per-run p99s,
not a pooled p99. Rejections and generator drops remain in the accounting.

Full commands, source fingerprints, binary SHA-256 hashes, settings, CPU/RSS
samples, I/O counters and queries are in each raw JSON report. See the
[procedure](../benchmarks.md) to reproduce a case; `environment.command` records
the exact selection and options. Normal `make benchmark` flags were used.

## Repeated C API throughput

Rows are 48 bytes with a numeric input ID, skewed site ID, path symbol, duration,
status and country. Unless listed otherwise: one producer, one table, 64-row
batches, 100 path symbols, 5 ms batching delay, 256 KiB target frames, and
256 MiB target segments. All these cases had zero rejected/failed rows and
zero generator drops.

| Case | Median rows/s | Range across runs | Median p99, ms | Highest process RSS, MiB |
| --- | ---: | ---: | ---: | ---: |
| Batch 1 | 71 | 69–74 | 18.9 | 2.44 |
| Batch 64 | 4,410 | 4,297–4,421 | 21.5 | 2.39 |
| Batch 1,024 | 63,971 | 60,922–73,611 | 25.1 | 3.02 |
| Maximum legal batch (21,791 rows), payload-capped | 1,548,087 | 1,541,957–1,616,384 | 22.5 | 13.14 |
| Four producers | 17,454 | 16,870–17,459 | 20.5 | 2.61 |
| Eight producers | 34,178 | 30,537–34,812 | 24.1 | 2.88 |
| Eight producers / eight tables | 8,463 | 8,421–8,542 | 86.0 | 3.36 |
| Four producers + concurrent aggregates | 18,141 | 18,072–18,699 | 18.4 | 3.50 |
| 100,000 paths, four producers, batch 1,024 | 228,554 | 224,663–229,220 | 30.2 | 15.70 |
| 4 KiB frame target, eight producers | 16,163 | 16,107–16,988 | 46.1 | 2.95 |
| No batching delay, four producers | 16,131 | 15,836–17,523 | 25.1 | 2.66 |
| 20 ms batching delay, four producers | 7,931 | 7,114–8,199 | 37.9 | 2.52 |
| 1 MiB segments, batch 1,024 | 61,086 | 58,435–66,400 | 47.1 | 3.20 |

Batching amortizes synchronization cost. Table count also matters: the single
writer synchronizes separate table files, and adjacent requests for different
tables cannot share one frame. The concurrent-query result overlaps ordinary
workstation variability; it is not evidence that adding queries improves writes.

## Repeated HTTP throughput and overload

The 48-byte HTTP cases use 64-row requests unless specified. Four producers feed
the ordinary and high-cardinality cases; scheduled arrivals, bursts, overload and
eight-table traffic use eight producers. The HTTP pool has four database workers.

| Case | Median committed rows/s | Range | Median arrival-to-ack p99, ms |
| --- | ---: | ---: | ---: |
| One table, saturation | 15,834 | 15,500–16,654 | 23.0 |
| Eight tables, saturation | 8,544 | 7,443–8,866 | 167.9 |
| Scheduled 10,000 rows/s | 9,986 | 9,985–9,990 | 37.9 |
| 100 ms bursts averaging 10,000 rows/s | 10,035 | 10,026–10,042 | 75.8 |
| Offered 1,000,000 rows/s | 19,549 | 19,047–19,631 | 3,801.1 |
| 100,000 paths, batch 1,024 | 234,345 | 230,221–253,822 | 24.1 |

All submitted requests in these trials committed; there were no HTTP append
rejections, indeterminate results or failures. Scheduled/burst cases accepted all
100,032 offered rows per run without generator drops. Burst throughput can exceed
the nominal rate slightly because the last burst arrives before the end of the
nominal window; draining and timer rounding explain the steady-rate difference.

The overload case offered 10 million rows per run. Across the three runs, the
bounded generator queue dropped **29,220,736 of 30 million offered rows**; the
remaining 779,264 committed. Its 13.3–13.4-second elapsed times include draining
the queue. Reporting its committed throughput alone would hide the enormous
offered-load deficit and roughly 3.8-second p99 queue delay. HTTP overload rejection
itself is exercised separately by the blocked-sync socket regression.

The highest server RSS was 24.94 MiB in the high-cardinality HTTP case; other
repeated HTTP cases stayed below 10 MiB. These are measured peaks for these
workloads, not the sum of all configurable memory budgets.

## Longer runs and the live console

All four longer workloads used 48-byte rows and 64-row requests, and all matched
successful receipts after restart. They are individual one- or two-minute trials,
not an endurance guarantee.

| Workload | Duration | Committed rows | Observed rows/s | Arrival-to-ack p99 |
| --- | ---: | ---: | ---: | ---: |
| C API, eight producers, saturation | 60.012 s | 1,848,320 | 30,799 | 27.1 ms |
| C API, eight producers, scheduled 10,000/s | 60.003 s | 600,000 | 9,999 | **5,374 ms** |
| HTTP, four producers, browser + queries | 60.009 s | 901,952 | 15,030 | 33.8 ms |
| HTTP, eight producers, 10,000/s + unread SSE client | 120.013 s | 1,200,000 | 9,999 | 75.8 ms |

The [engine report](macos-sustained-engine.json) shows no rejected, failed or
generator-dropped rows. However, its paced run accumulated substantial generator
queue delay: median arrival-to-ack was 737 ms and p99 was 5.37 seconds, while
API-call p99 was 86.0 ms. It eventually caught up within the measurement window.
This demonstrates why average throughput alone cannot establish a latency SLO.
The cause of the variable service rate was not isolated; do not ascribe it solely
to the filesystem or dismiss it as measurement noise.

Two [additional identical 60-second paced trials](macos-paced-repeat.json)
each committed all 600,000 offered rows with zero drops/rejections/failures.
Arrival-to-ack p99s were 672 and 688 ms; API-call p99s were 42.0 and 34.8 ms.
All three paced results are retained. The initial multi-second backlog did not
recur at that magnitude, but the repeats still show material queue delay.

The actual [browser run](macos-browser.md) rendered the overview and then the
sampled live feed while an external client also ran monitoring and 53 successful
aggregates. No append failures/rejections or browser errors were observed during
ingestion. Server peak RSS was 11.8 MiB and restart took 208 ms. The linked page
contains screenshots and the raw measurement report.

The [independent slow-reader run](macos-slow-reader.json) committed every one of
its 1.2 million scheduled rows with no drops/rejections/failures. Its unread SSE
socket closed, the fast reader received 478 commit and 119 statistics events,
and all 119 polling cycles completed without rejection. The one reset was the
expected initial subscription without a boot/feed cursor, not a subsequent gap.
Server peak RSS was 13.2 MiB; restart took 246 ms. Both stops exited cleanly.

## Measured tuning decision

The [exploratory baseline](macos-exploratory-baseline.md) exposed unnecessary
HTTP rejection when every small append reserved 4 MiB of response memory. The
implemented change reserves and enforces a 4 KiB append response bound before
dispatch; other endpoints retain 4 MiB, and global/queue limits remain enforced.
API and blocked-sync tests verify the bound and rejection before mutation.

The repeated post-change burst cases accepted every offered row; the earlier
two-second burst baseline rejected 11,072 rows. Eight-table post-change runs also
had no admission rejections. Different durations and host variability preclude a
precise throughput speedup claim from this comparison; the admission regression
isolates the cause independently.

Keep the 5 ms batching delay and 256 KiB frame target: zero delay gave no consistent
throughput gain, 20 ms worsened throughput/latency, and 4 KiB frames roughly halved
eight-producer throughput. Keep 256 MiB default segments: 1 MiB segments increased
rotation-related p99 while offering faster startup of the smaller active tail.
The segment setting remains a retention/recovery granularity tradeoff.

## Storage cost, queries and retention

Median OS-reported write bytes per logical payload byte were 266.50 for single-row
requests, 6.07 for batches of 64, 1.32 for batches of 1,024, and 1.014 for maximum
batches. These counters include filesystem/block accounting and repeated writes;
they are **not physical flash write amplification**. Median final source/payload
ratios were respectively 3.098, 1.0325, 1.0020 and 1.00011. Final file footprint
and cumulative writes measure different costs.

For one representative 512 MiB maximum-batch fixture, dictionaries occupied 7,512
bytes, segment/frame overhead 49,728 bytes, derived indexes 38,032 bytes and
metadata 1,049 bytes. The high-cardinality fixture stored 2.5 MB of dictionary
definitions for its 100,000 symbols. Dictionary/index/source sizes are retained
per case in the raw report rather than extrapolated across arbitrary schemas.

On the three 1,024-row-batch fixtures, a recent 100-row tail read scanned 51,752
bytes and took 0.20–0.28 ms. Broad count/sum scanned 29.3–35.4 MB and took
126.9–166.2 ms across first/repeated executions. Minute/hour/day queries all span
these short fixtures; use the [multi-day Linux result](linux-memory-2026-09-28.md)
for selective time-range and verified cold-page evidence. Reopening does not make
macOS caches cold. Normal warm/repeated query results are labeled accordingly.

Top-path grouping over 100,000 paths returns `resource_limit` at the default
10,000-group budget. The rows remain readable and broad count/sum succeeds.
Increase a query's explicit group/memory budgets when appropriate, or design
derived rollups later; the engine does not silently approximate.

Three retention trials each retired 262,144 rows in 13 segments (12,641,704 source
bytes). A pre-existing cursor kept every source byte readable after retirement,
while new readers saw no retired rows. Durable retirement took 5.7–6.7 ms;
releasing the cursor and deleting the files took 1.9–3.2 ms. All source/index
files disappeared, restart took 0.38–0.43 ms, and sequence 262,145 was appended
and verified through another restart. Tombstone metadata remains by design.

The raw sequential references each wrote/synchronized 64 MiB on the same APFS
volume. With one full synchronization per 256 KiB block, observed throughput was
30.7 MB/s; with 1 MiB blocks, 107.9 MB/s. These short references show how
synchronization granularity changes the result. They are not an absolute device
ceiling or a competing-database result.

## Coverage and failure model

The broader [exploratory sweep](macos-exploratory-baseline.json) contains 45 verified
cases covering 32/48/128/512/8,192-byte rows, legal submission batch sizes, repeated
timestamps, rates/bursts, tables, frame/segment settings and HTTP paths. It has
one repetition and mostly two-second windows, so only the later repeated/longer
cases support the bounded capacity conclusions here. Its incomplete final
slow-reader case is explicitly labeled; it is superseded by the separate long run.

The [Linux memory report](linux-memory-2026-09-28.md) verifies a 512 MiB dataset
inside a 256 MiB, two-CPU container with no additional swap allowance. It includes
exact post-restart aggregates, successful queries after `mincore`-verified guest
page eviction, a 20.7 MiB ingest-process peak RSS, and zero OOM events. Host/device
caches were not flushed; this is not native Linux disk capacity.

Both supported platforms pass 77 correctness tests and AddressSanitizer plus
UndefinedBehaviorSanitizer. ThreadSanitizer coverage, the 217-point termination
matrix, 144 injected I/O failures, actual full-disk recovery and stopped-copy
restore are documented in [platform validation](../platform-validation.md),
[failure testing](../failure-testing.md) and [operations](../operations.md).

Successful appends synchronize their authoritative frames before acknowledgement.
Interrupted incomplete tails recover to a complete prefix; complete corruption
fails closed. Lost responses/indeterminate outcomes can still represent committed
rows, so retries can duplicate data. Process-crash tests do not simulate physical
power removal, media loss or every filesystem/device implementation.

Prioritize client batching and bounded offered rates when sizing deployments.
The next storage optimization to investigate is a derived representation for
broad aggregates (columnar projections or rollups); sparse indexing already
reduces narrow-range work, while broad queries scan source rows. Native Linux
capacity and longer endurance trials should be performed on the intended
deployment hardware before using these workstation results as an operational SLO.
